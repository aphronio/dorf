Exploration brief

A leadership layer for AI software delivery

Explore whether a small set of role-focused agents can preserve product intent and engineering judgment across downstream implementation work—without adding ceremonial process.

The premise

High-quality software work improves when someone holds the broader vision in conversation: challenging unnecessary scope, checking whether existing capabilities can be reused, and making trade-offs explicit before code is written. This proposal experiments with making that alignment role persistent and scalable.

Proposed operating model

CEO agent

Protects company values, customer impact, priorities, economics, and product coherence. It is consulted only when a proposed solution changes one of those concerns.

CTO agent

Protects architecture, maintainability, reliability, reuse, and long-term engineering leverage. It is the normal decision partner for implementation work.

Software engineer agent

Owns the concrete plan, issue details, implementation, and evidence of completion. It should propose the smallest sound solution rather than receive a prescriptive build script.

Decision flow

1 · IntentHuman states the desired outcome and relevant context.
2 · FramingCTO evaluates feasibility, constraints, and implementation options.
3 · Trade-offCTO consults CEO only for material product, cost, or principle decisions.
4 · DeliveryEngineer writes the issue and plan, then implements within the agreed boundary.
Default rule: Do not make every task a three-way discussion. The CTO and engineer handle normal execution; the CEO is a focused escalation path, not a second technical reviewer.

Decision rights and escalation

  • The engineer can choose implementation details inside the approved boundary.
  • The CTO can reject unnecessary complexity, require reuse, and approve architectural direction.
  • The CEO weighs meaningful scope, customer, priority, and cost trade-offs.
  • The human is involved when a decision changes strategy, creates an irreversible commitment, materially increases risk or spend, or lacks a clear value judgment.

Artifacts that preserve context

  • Project charter: durable company vision, principles, product boundaries, and success measures.
  • Engineering charter: architectural principles, reuse expectations, quality bar, and explicit non-goals.
  • Decision log: brief records of important trade-offs, including why alternatives were declined.
  • Issue: authored by the engineer after alignment; captures goal, non-goals, smallest viable approach, acceptance criteria, and open risks. This brief is its conceptual reference.

Building-block standard: earn the right to exist

The system should favor small, composable building blocks with excellent developer experience. Existing tools are the default; adapters should make capabilities swappable without inventing abstractions before they are needed.

Value gate: before building a new capability, identify the best existing alternative and state the intended step-change. A new building block should be at least 10× better on one meaningful axis—such as developer time, reliability, cost, latency, operational effort, or user experience—or unlock a composition that existing options cannot reasonably provide.
  • Research first: compare mature tools, libraries, services, and internal capabilities before proposing custom work.
  • Choose deliberately: adopt, integrate, adapt with a thin adapter, or build. Building is the exception, not the default.
  • Name the baseline: define what “10×” is relative to, who benefits, and how the claim will be tested.
  • Prefer reversible seams: isolate provider-specific code and keep the interface no more general than actual current use requires.
  • Stop when the case is weak: if no meaningful advantage is plausible, reuse the existing solution instead of recreating it.

The 10× standard is a strategic test, not an excuse for artificial metrics. A capability can earn its place through one decisive advantage; multiple improvements are a bonus.

Choose opportunities before features

The 10× test is not merely a brake on custom code. It is a compass for deciding where to invest. Start by looking for high-impact parts of the workflow where current technology creates a credible opportunity for a discontinuous improvement. Then direct product and engineering effort toward those areas.

  • Potential: can current technology plausibly make this workflow dramatically better than the best available approach?
  • Impact: if successful, would the improvement matter materially to customers, the business, or the engineering system?
  • Strategic fit: does this strengthen the distinctive system the company wants to own?
  • Focus: where an area is already good enough or undifferentiated, reuse the best option and preserve attention for a higher-leverage opportunity.

Evaluate the whole workflow, not only an isolated component. The largest advantage may come from removing handoffs, making context persistent, or combining existing tools into a much simpler experience.

Experiment to validate the model

Trial the model on a small set of medium-sized changes. Compare it with normal agent execution, using the same kinds of work where possible.

  • Measure rework, scope creep, patch size, time to a trusted result, and how often human intervention is needed.
  • Review whether the leadership layer caught a real issue early, or merely produced extra discussion.
  • Keep its required output short: an agreed boundary and a decision record, not elaborate plans.
  • Refine escalation thresholds after each trial; remove roles or steps that do not improve outcomes.

Success is not more agent activity. Success is clearer decisions, smaller and more coherent changes, less rework, and fewer high-attention interventions from the human.
